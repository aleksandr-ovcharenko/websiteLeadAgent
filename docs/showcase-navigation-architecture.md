# Showcase Navigation — Current Architecture & Root Gaps

> Investigative baseline for the navigation rewrite. Code was inspected on the running `8e25ix7c` site; database state was read from `__CMS__` output and the `MenuItem` schema.

## 1. Where Header navigation comes from

**Current source:** `packages/templates/src/construction-modern-v1/index.ts` builds a `NAV` array from `ctx.menu` (Prisma `MenuItem`) and falls back to `DEFAULT_CMS.NAV` only when no menu exists.

`Header` in `App.tsx` renders:

```tsx
(NAV || []).filter((n: any) => n.showInHeader).map(...)
```

`showInHeader` is **not a real database field** — `index.ts` blindly sets `showInHeader: item.showInHeader !== false` for every row, so the server sets `true` for everything unless the object already carries the property from `DEFAULT_CMS`.

## 2. Where Footer navigation comes from

**Current source:** the same `NAV` array.

`Footer` in `App.tsx` renders `NAV.filter(n.showInFooter)` for the first column, then renders a hardcoded `SERVICES.slice(0,6)` list in the second column.

So the Footer has **two separate navigation sources**:
- `NAV` for generic pages/sections.
- `SERVICES` array for service links.

## 3. How Homepage section order is currently defined

**Hardcoded in JSX.** `Home` in `App.tsx` (line 1851) is a static component list:

```tsx
<Home>
  <Hero />
  <About />
  <Services />
  <Projects />
  <Process />
  <News />
  <VacancyList />
  <CTA />
</Home>
```

`NAV` is not used to decide which sections appear or in what order. CMS `sortOrder` has no effect on the homepage layout.

## 4. Which Homepage sections are hardcoded in JSX

All business sections are hardcoded React components:

- `About`
- `Services` (also used as the `ServiceList` component)
- `Projects` (also used as the `ProjectList` component)
- `Process`
- `NewsList`
- `VacancyList`
- `CTA` (contacts)

Only `id` attributes (`#about`, `#services`, `#projects`, `#news`, `#vacancies`, `#contacts`) give them anchors. `Process` has no `NAV` equivalent.

## 5. Current `MenuItem` fields/model

From `prisma/schema.prisma`:

```prisma
model MenuItem {
  id        String
  siteId    String
  menuId    String
  label     String
  pageId    String?
  url       String?
  targetType String?  // HOME, HOME_SECTION, PAGE, CONTENT_DETAIL, CUSTOM_URL, EXTERNAL_URL
  target    String?
  parentId  String?
  sortOrder Int      @default(0)
  visible   Boolean  @default(true)
  // ...timestamps, relations
}
```

**Missing fields:** `showInHeader`, `showInFooter`, `showOnHomepage`.

## 6. How CMS currently saves navigation

`apps/cms/src/server.ts` `/api/cms/sites/:siteId/menu` PUT handler deletes old items and re-creates `MenuItem` rows from the NavEditor payload. It currently writes:

```ts
{
  label, pageId, url, targetType, target, sortOrder, visible, parentId
}
```

Visibility and placement flags (`showInHeader`, `showInFooter`, `showOnHomepage`) are **not persisted** because they do not exist in the data model.

## 7. Which links come from CMS

Only top-level `MenuItem` rows that survived the `resolveNavHref` resolution. The renderer injects them into `window.__CMS__.NAV`.

On the running `8e25ix7c` site, `__CMS__.NAV` is:

```
Главная     → /showcase/8e25ix7c/        (HOME)
Услуги      → /showcase/8e25ix7c/#services (HOME_SECTION SERVICES)
Объекты     → /showcase/8e25ix7c/#projects (HOME_SECTION PROJECTS)
О компании  → /showcase/8e25ix7c/#about    (HOME_SECTION ABOUT)
Новости     → /showcase/8e25ix7c/#news     (HOME_SECTION NEWS)
Контакты    → /showcase/8e25ix7c/#contacts (HOME_SECTION CONTACTS)
Вакансии    → /showcase/8e25ix7c/#vacancies (HOME_SECTION VACANCIES)
```

All `showInHeader` / `showInFooter` / `showOnHomepage` are `true` at runtime because `index.ts` hardcodes them.

## 8. Which links are generated by the renderer/template

`packages/templates/src/construction-modern-v1/index.ts` `resolveNavHref` generates these:

- `HOME` → `/showcase/:token/`
- `HOME_SECTION` → `/showcase/:token/#<target>`
- `PAGE` → `/showcase/:token/<pageSlug>`
- `CONTENT_DETAIL` → `/showcase/:token/<type>/<slug>`
- `CUSTOM_URL` / `EXTERNAL_URL` → literal or absolute

It does **not** have a `COLLECTION` target type.

## 9. Which links are hardcoded

Hardcoded or label-based links in `App.tsx` (non-exhaustive):

- Brand logo: `PREVIEW_TOKEN ? /showcase/${PREVIEW_TOKEN} : '#'` — OK, but still hardcoded.
- Header phone: `COMPANY.phoneHref` (tel:) — OK.
- Header CTA "Обсудить проект": `navHref('Контакты')` — label-based.
- Hero CTA "Обсудить проект": `navHref('Контакты')`.
- Hero "Портфолио": `navHref('Объекты')`.
- `About` "Подробнее о компании": `href="/about"` — **wrong base path, missing preview token, not semantic**.
- `Process` step links: `step.href` from hardcoded `PROCESS_STEPS`.
- `News` "Все новости" / "Все новости →": `navHref('Новости')` — **goes to `#news`, not the collection page `/news`**.
- `Project` "All objects"? none found.
- `Service` "All services"? none found.
- `Footer` "Пригласить на тендер": `mailto:...` — OK.
- `Footer` "Услуги" service list: `serviceHref(s.slug)` — generated, but from `SERVICES`, not `NAV`.
- Detail back links: `sectionHref('NEWS')` etc — always back to **homepage section**, no context.

## 10. Which links came directly from the Figma prototype

No Figma-generated code references were found in the repo. However, the current `App.tsx` components and section order follow the original visual layout. The `About` `href="/about"` and the `Process` `step.href` values are likely legacy prototype values that were never made semantic.

## 11. Current collection routing

**Not implemented.** There is no collection list route.

`site-renderer/src/server.ts` `fmtRoute` turns `/showcase/:token/<route>/<subRoute>` into `{ route, subRoute }`.

- `/showcase/:token/services` → `route='services', sub=''`
- `/showcase/:token/services/<slug>` → `route='services', sub='<slug>'`

`App.tsx` treats `route === 'services' && !sub` as a **homepage section** (`isHomeSection`) and renders `Home` with scroll to `#services`. It does **not** render a full `ServiceList` collection page.

Therefore `/showcase/:token/services` is currently indistinguishable from `/#services`.

## 12. Current detail routing

Detail routes exist and work:

- `/showcase/:token/news/:slug` → `NewsDetail`
- `/showcase/:token/projects/:slug` → `ProjectDetail`
- `/showcase/:token/services/:slug` → `ServiceDetail`
- `/showcase/:token/vacancies/:slug` → `VacancyDetail`

Card links use `newsHref`, `projectHref`, `serviceHref`, `vacancyHref`.

## 13. Current "Back to..." implementation

All detail back links call `sectionHref('NEWS'|'PROJECTS'|'SERVICES'|'VACANCIES')` which always resolves to the homepage section anchor.

There is **no context awareness**: whether the user came from the homepage section or from a collection page, the back link always returns to `/#<section>`.

## 14. Current behavior of "All news", "All projects", "All services", etc.

Only "Все новости" exists. It uses `navHref('Новости')`, which maps to the `Новости` `HOME_SECTION` item and goes to `/#news`.

There is no link to the `News` collection (`/news`). `Projects`, `Services`, and `Vacancies` home sections have no "All..." CTA at all.

## Root Architectural Gaps

### Gap 1: Missing visibility fields in `MenuItem`

`showInHeader`, `showInFooter`, `showOnHomepage` do not exist in the database. The server fakes `true` for everything. Header, Footer, and Homepage cannot be independently controlled.

### Gap 2: Homepage order is hardcoded, not CMS-driven

The `Home` component lists sections statically. CMS `sortOrder` and `showOnHomepage` are ignored.

### Gap 3: No `COLLECTION` semantic target type

The resolver only knows `HOME_SECTION` (anchor) and `CONTENT_DETAIL` (single item). It cannot generate a collection page URL (`/showcase/:token/news`) for a menu item or a CTA.

### Gap 4: No collection page components or routes

`route === 'news' && !sub` is treated as a homepage section. A real `/news` standalone page showing all items does not exist.

### Gap 5: Context-unaware back navigation

Detail pages always return to `/#section`. They cannot return to the collection page when the user arrived from a collection.

### Gap 6: Multiple navigation sources / hardcoded links

- Footer service list comes from `SERVICES` array, not `NAV`.
- `About` CTA is `href="/about"` with no preview token.
- Process steps use a hardcoded `href` array.
- Hero, About, and News CTAs use label-based `navHref` rather than semantic `targetType`.

### Gap 7: Figma/prototype values still present

`About` `href="/about"` and `Process` step links are likely leftover prototype paths.

### Gap 8: `NavEditor` cannot control visibility

The Studio UI has no toggles for `showInHeader`/`showInFooter`/`showOnHomepage`.

### Gap 9: Validation for disabled homepage sections

There is no CMS/API validation for the case `targetType === HOME_SECTION && showOnHomepage === false`.

---

## Required model changes

1. Add `MenuItem.showInHeader`, `MenuItem.showInFooter`, `MenuItem.showOnHomepage` columns.
2. Add `COLLECTION` to `MenuItem.targetType` enum/values.
3. Update `NavEditor` to set visibility and `COLLECTION` targets.
4. Update `resolveNavHref` to handle `COLLECTION`.
5. Refactor `App.tsx`:
   - `Home` renders sections from `NAV.filter(showOnHomepage)` in `sortOrder`.
   - `Header` and `Footer` use the same `NAV` with their own filters.
   - Add `NewsCollection`, `ProjectsCollection`, `ServicesCollection`, `VacanciesCollection` routes/components.
   - Make detail back-links context-aware (`returnTarget` via `cms.returnTarget` or query param).
6. Replace label-based `navHref` calls with semantic helpers (`navHrefByTarget`, `collectionHref`, `sectionHref`).
7. Add collection CTAs to homepage sections.
8. Remove hardcoded prototype links.
