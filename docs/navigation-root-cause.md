# Showcase Navigation — Root Cause Analysis

## 1. Which links currently come from CMS `MenuItem` data

The `Header` and `Footer` in `packages/templates/src/construction-modern-v1/App.tsx` render from `__CMS__.NAV`. `NAV` is produced in `packages/templates/src/construction-modern-v1/index.ts` from `ctx.menu` (`MenuItem` rows loaded by `apps/site-renderer/src/server.ts`).

Examples for the Garant site:

- `О компании` → `__CMS__.NAV` from `Page.slug = about`
- `Услуги` → from `MenuItem.url = /services` or `Page.slug = services`
- `Новости` → from `MenuItem.url = /news` or `Page.slug = news`
- `Контакты` → from `Page.slug = contacts`

These are the links that should be CMS-driven and the target of this fix.

## 2. Which links are generated by the template

`App.tsx` contains helper functions that generate detail and section URLs from `__CMS__` data:

- `newsHref(slug)` → `/showcase/:previewToken/news/:slug`
- `projectHref(slug)` → `/showcase/:previewToken/projects/:slug`
- `serviceHref(slug)` → `/showcase/:previewToken/services/:slug`
- `vacancyHref(slug)` → `/showcase/:previewToken/vacancies/:slug`
- `navHref(label)` → looks up `__CMS__.NAV` by `label` and returns its `href`

The detail-card links (news, project, service, vacancy cards) use these helpers. Back links (`← Назад к …`) use `navHref(label)`. These are already mostly dynamic, but they consume `NAV` whose `href` values are wrong.

## 3. Which links are hardcoded in React components

- `DEFAULT_CMS.NAV` in `App.tsx` is a fallback with `href: '#services'`, `href: '#about'`, etc. It is used only when `window.__CMS__` is missing, but it is **semantically inconsistent** with the real server-generated `NAV`.
- The CTA sections use `navHref('Контакты')`.
- `NewsDetail` uses a hardcoded back link: `PREVIEW_TOKEN ? /showcase/${PREVIEW_TOKEN} : '#'` instead of the News section.
- The `Footer` bottom bar previously contained `/vacancies`; after the last fix it uses `navHref('Вакансии')`.
- `DEFAULT_CMS` contains hardcoded company data, phone, domain (`example.com`) and fallback navigation.

No Garant-specific `previewToken` is currently hardcoded, but `DEFAULT_CMS` is not generic.

## 4. Which routes came from the Figma prototype

The following path-based routes are present only because the Figma/prototype implementation treated every menu item as a page URL:

- `/showcase/:previewToken/services` → `ServiceList`
- `/showcase/:previewToken/projects` → `ProjectList`
- `/showcase/:previewToken/news` → `NewsList`
- `/showcase/:previewToken/vacancies` → `VacancyList`
- `/showcase/:previewToken/about` → rendered by `PageView` if `Page.slug = about`
- `/showcase/:previewToken/contacts` → rendered by `PageView` if `Page.slug = contacts`

These are the “invented collection pages” that must be replaced by homepage section anchors for the current template.

## 5. Which standalone collection routes exist only because of the previous prototype

`apps/site-renderer/src/server.ts` has a generic `fmtRoute` that takes any first path segment as `route` and the rest as `subRoute`. `App.tsx` then matches:

```
route === 'news' && !sub   → NewsList
route === 'news' && sub    → NewsDetail
route === 'projects' && !sub → ProjectList
...
route === 'vacancies' && !sub → VacancyList
...
```

The `NewsList`, `ProjectList`, `ServiceList`, and `VacancyList` components render full collection pages with `id="news"`, `id="projects"`, `id="services"`, `id="vacancies"`. For this template these should not be reachable as standalone routes; they should only appear as sections of the homepage.

`PageView` with `id={slug}` for arbitrary `Page` records is generic and useful for standalone pages such as `privacy`, but `about` and `contacts` should also resolve to the homepage for the current template.

## 6. Whether current navigation data can express `HOME_SECTION` semantics

**No.**

`prisma/schema.prisma` `MenuItem` model:

```prisma
model MenuItem {
  id        String   @id @default(cuid())
  siteId    String
  menuId    String
  label     String
  pageId    String?
  url       String?
  parentId  String?
  sortOrder Int      @default(0)
  visible   Boolean  @default(true)
  ...
}
```

The model only knows `pageId` (foreign key to a `Page`) and `url` (free text). It has no `targetType`, `sectionKey`, `external` flag, or `showInHeader/showInFooter/showOnHomepage` columns.

`apps/platform/src/cms/NavEditor.tsx` does show a `type` dropdown (`page`, `section`, `external`), but `treeToFlat` sends `type` in the PUT body and `apps/cms/src/server.ts` **does not persist it**:

```ts
await (prisma as any).menuItem.create({
  data: { siteId, menuId: menu.id, label: item.label || item.title, pageId: item.pageId || null, url: item.url || null, sortOrder: i, visible: item.isVisible !== false, parentId }
});
```

So the Studio UI hints at semantic types, but the database and renderer cannot see them.

## Root cause

The renderer (`packages/templates/src/construction-modern-v1/index.ts` `resolveNavHref`) treats every `MenuItem` as either an external URL or a real path:

- If `page.slug` exists → `/showcase/:previewToken/:pageSlug`
- If `url` exists → `/showcase/:previewToken/:url`

Because there is no `targetType` field, the renderer has no way to know that `Услуги` should map to the homepage section `#services`, that `О компании` should map to `#about`, or that `Вакансии` should map to `#vacancies`. It invents a standalone page/collection route for every item.

The client-side `navHref(label)` simply returns whatever `__CMS__.NAV` produced, so `Header`, `Footer`, CTAs, and detail back-links all point to those invented collection routes instead of the intended homepage anchors.

The `App.tsx` fallback (`DEFAULT_CMS.NAV`) and the `NavEditor` UI both know about `section` anchors, but this knowledge is lost before it reaches the server and the renderer.

## Before / After model

| Concern | Before | After |
| --- | --- | --- |
| CMS data for menu | `pageId` + raw `url` string | `targetType` + `target` + `url` for custom/external |
| URL generation | `resolveNavHref` builds `/showcase/:token/:slug` for every item | Resolver builds `/#section` for `HOME_SECTION`, `/:pageSlug` for `PAGE`, full detail URL for `CONTENT_DETAIL`, literal for `CUSTOM`/`EXTERNAL` |
| Header/Footer links | point to `/services`, `/news`, `/about` | point to `/showcase/:token/#services`, `#news`, `#about` |
| Back links from detail | `navHref(label)` → collection list route | `navHref(label)` → homepage section anchor |
| Detail URLs | `/showcase/:token/:collection/:slug` (already correct) | keep exact same `/showcase/:token/:collection/:slug` |
| Collection list URLs | `/showcase/:token/news`, etc. | removed for this template; only the homepage section exists |
